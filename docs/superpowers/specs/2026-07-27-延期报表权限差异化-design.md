# 延期任务报表权限差异化设计

> 创建日期：2026-07-27
> 状态：待审阅
> 作者：AI 助手 + 用户协作设计

---

## 1. 背景与目标

当前「延期分析报表」Tab 对所有经理角色（admin / dept_manager / tech_manager）展示**相同的图表组合**，仅数据范围按角色自动隔离（`buildTaskScopeFilter`）。用户希望针对不同权限设计**差异化视图**，使管理者能从团队整体、成员个人、问题任务三个层面，静态+动态多维度地审视延期，发现改善机会。

### 核心目标
1. **按角色差异化**：同页内按角色渲染不同的区块组合（非独立 Tab）。
2. **三视角全覆盖**：团队整体（哪里最严重）、成员个人（谁需改善）、问题任务（哪些任务反复延期）。
3. **静态+动态**：当前快照指标 + 历史趋势/改善环比。
4. **纯多维数据展示**：不生成智能标注或文字建议，由用户自行解读（KISS/YAGNI）。

### 非目标（不做）
- 不新增独立报表 Tab（沿用现有「延期分析报表」Tab）。
- 不做智能改善建议 / 归因文字生成。
- 不改动数据隔离口径与 WBS 编码单一源头机制。
- 不调整 `app/server/src/migrations/`（红线）。

## 2. 角色与数据范围

| 角色 | 数据范围 | 报表权限 |
|---|---|---|
| `admin` | 全公司 | ✅ |
| `dept_manager` | 本部门 + 所有子部门（多个技术组） | ✅ |
| `tech_manager` | 本技术组 + 授权组（单组/几组） | ✅ |
| `engineer` | 自己参与的项目 | ❌ 无 `REPORT_VIEW`（现状，不改） |

**数据隔离复用现有机制（零改动）**：
- 任务范围：`buildTaskScopeFilter(user)`（`analytics/query-builder.ts`）
- 用户/部门范围：`buildUserDepartmentScopeFilter(user)`
- 部门树解析：`getManagedDepartmentIds`（dept_manager）/ `getTechManagerGroupIds`（tech_manager）

## 3. 三视角维度清单

### 🏢 团队视角（T1~T8）— 看整体/组间，识别"哪里最严重"

| # | 维度 | 指标 | 数据来源 |
|---|---|---|---|
| T1 | 组间排名对比 | 各组：延期数、延期率、平均延期天数、累计延期次数、计划变更次数 | `users.department_id` GROUP BY |
| T2 | 团队整体指标卡 | 总延期、预警、超期完成 + **累计延期总次数** + **计划变更总次数** | 聚合 wbs_tasks |
| T3 | 严重度分布 | 轻<7天 / 中7-30天 / 重>30天 占比 + 平均延期天数 | `DATEDIFF(CURDATE(), end_date)` 分桶 |
| T4 | Top 延期原因 | 团队层面原因排行（数量+占比） | `delayed_tasks.reason` 聚合 |
| T5 | 延期趋势 + 改善环比 | 新增/解决/收敛扩散 + 本期 vs 上期（改善/恶化） | `delay_trend` 当周 vs 上周 |
| T6 | 项目维度 | 项目延期数、项目延期率排名 | `project_id` GROUP BY |
| T7 | 任务类型维度 | 任务类型 × 延期率（哪类任务易延期） | `task_type` GROUP BY |
| T8 | 预估偏差维度 | 计划工期 vs 实际工期偏差、预估准确性分布（±10%/10-30%/30-50%/>50%） | `planned_duration` vs `actual_duration` |

### 👤 个人视角（P1~P5）— 看成员个体，识别"谁需要改善"

| # | 维度 | 指标 | 数据来源 |
|---|---|---|---|
| P1 | 成员延期排名 | 每人：当前延期数、累计延期次数、计划变更次数、平均延期天数 | `assignee_id` GROUP BY |
| P2 | 原因×责任人交叉 | 每个成员的延期主因（矩阵） | `reason` × `assignee_id` |
| P3 | 成员明细表 | 成员统计（含累计/计划变更列）→ 下钻看该成员延期任务列表 | 复用 `delayed_member_stats` 增强 |
| P4 | 反复延期识别 | 高 `delay_count` 人员突出（累计延期次数排名置顶） | `wbs_tasks.delay_count` |
| P5 | 成员个人延期趋势 | **Top N（默认10）成员**的延期数随时间变化 | per-member 时间序列 |

### 📋 任务视角（K1~K2）— 识别"问题任务"

| # | 维度 | 指标 | 数据来源 |
|---|---|---|---|
| K1 | 反复延期任务榜 | 按 `delay_count` 降序的任务列表（任务名/项目/责任人/当前延期天数/累计延期次数/计划变更次数） | `wbs_tasks.delay_count` |
| K2 | 频繁变更任务榜 | 按 `plan_change_count` 降序的任务列表 | `wbs_tasks.plan_change_count` |

## 4. 角色 × 视角可见性

| 视角 | admin | dept_manager | tech_manager |
|:---:|:---:|:---:|:---:|
| 🏢 团队（T1~T8） | ✅ 全公司 | ✅ 管辖各组 | ✅ 本组聚合 |
| 👤 个人（P1~P5） | ✅ 全员 | ✅ 管辖成员（可按组筛） | ✅ 本组成员 |
| 📋 任务（K1~K2） | ✅ 全部 | ✅ 管辖范围任务 | ✅ 本组任务 |

**T1 组间排名**的特殊处理：
- admin / dept_manager：渲染"各组延期对比"（多组才有对比意义）。
- tech_manager：通常只管 1 组，**不渲染组对比**，改为渲染"本组总览指标卡"（单组聚合 = T2 的子集）。

**每个角色都同时拥有三视角**（范围不同，维度齐全）。

## 6. 后端扩展

### 6.1 接口
扩展现有 `GET /api/analytics/reports/delay-analysis`（不新建接口），返回字段增量。

### 6.2 `DelayAnalysisReport` 新增字段

```typescript
// analytics/types.ts
interface DelayAnalysisReport {
  // —— 现有（保留，不改动）——
  total_delayed: number;
  warning_count: number;
  delayed_count: number;
  overdue_completed_count: number;
  delay_reasons: DelayReasonCount[];
  delay_trend: TrendDataPoint[];
  delayed_tasks: DelayedTaskItem[];
  delayed_member_stats: DelayedMemberStat[];
  warning_member_stats: WarningMemberStat[];

  // —— 新增：团队视角 ——
  team_comparison: DepartmentDelayStat[];      // T1 组间排名（admin/dept_manager）
  severity_distribution: {
    mild: number;       // <7天
    moderate: number;   // 7-30天
    severe: number;     // >30天
    avg_delay_days: number;
  };                                            // T3
  project_delay_stats: ProjectDelayStat[];      // T6
  task_type_delay_stats: TaskTypeDelayStat[];   // T7
  estimation_deviation: {
    avg_deviation_days: number;
    accuracy: { accurate: number; slight: number; obvious: number; serious: number };
  };                                            // T8
  improvement_trend: {
    current_delayed: number;
    previous_delayed: number;
    delta: number;
    direction: 'improving' | 'worsening' | 'flat';
  };                                            // T5 环比

  // —— 新增：个人视角 ——
  member_ranking: MemberDelayStat[];            // P1（增强列）
  member_trends: MemberTrendPoint[];            // P5（Top N 成员趋势）
  reason_member_matrix: ReasonMemberCell[];     // P2 原因×责任人交叉

  // —— 新增：任务视角 ——
  repeat_delay_tasks: DelayedTaskItem[];        // K1 按 delay_count 降序 Top N
  frequent_change_tasks: DelayedTaskItem[];     // K2 按 plan_change_count 降序 Top N
}

// 新增类型
interface DepartmentDelayStat {
  dept_id: number;
  dept_name: string;
  total_tasks: number;
  delayed_count: number;
  delay_rate: number;            // %
  avg_delay_days: number;
  total_delay_count: number;     // 累计延期次数（sum delay_count）
  plan_change_count: number;
}

interface MemberDelayStat {
  assignee_id: number;
  assignee_name: string;
  delayed_task_count: number;    // 当前延期任务数
  total_delay_count: number;     // 累计延期次数
  plan_change_count: number;
  avg_delay_days: number;
}

interface ProjectDelayStat {
  project_id: string;
  project_name: string;
  total_tasks: number;
  delayed_count: number;
  delay_rate: number;
}

interface TaskTypeDelayStat {
  task_type: string;
  total_tasks: number;
  delayed_count: number;
  delay_rate: number;
}

interface MemberTrendPoint {
  assignee_id: number;
  assignee_name: string;
  points: { date: string; delayed: number }[];
}

interface ReasonMemberCell {
  reason: string;
  assignee_id: number;
  assignee_name: string;
  count: number;
}
```

### 6.3 SQL/查询要点
- **T1 组间**：`buildUserDepartmentScopeFilter` 拿可见部门 → JOIN users 按 `department_id` GROUP BY。
- **T6/T7**：在 `buildTaskScopeFilter` 内按 `project_id` / `task_type` GROUP BY。
- **T3 严重度**：对已隔离的延期任务用 `CASE WHEN DATEDIFF(CURDATE(), t.end_date) < 7 ...` 分桶。
- **T8 预估偏差**：`actual_duration - planned_duration`（仅完成延期任务有 actual_duration）。
- **T5 改善环比**：`delay_trend` 最后一周 vs 前一周的 delayed 值比较。
- **K1/K2**：在 scope 内 `ORDER BY delay_count DESC / plan_change_count DESC LIMIT N`。
- **P2 原因×责任人**：`GROUP BY reason, assignee_id`，前端透视成矩阵。
- **P5 成员趋势**：先取 Top N（P1 排名前 N），再为这 N 人查 per-week 延期数时间序列。

### 6.4 口径约束（红线）
- 所有"延期"判定与 WBS 表 `computed_status` 基准一致（遵循 `task-status-wbs-source-of-truth`），用 `STATUS_CONDITIONS.delayed`（`actual_end_date IS NULL AND end_date < CURDATE()`）。
- 预警用 `STATUS_CONDITIONS.delayWarning`。
- `delay_count` / `plan_change_count` 直接读 `wbs_tasks` 字段（不重算）。
- WBS 编码经 `getUserWbsCodeMap` 单一源头获取（不独立计算）。

## 9. 性能与实现约束

- **P5 成员趋势限 Top N（默认 10）**：避免全员 per-week 时间序列数据量爆炸。
- **K1/K2 限 Top N（默认 10）**：问题任务榜只展示最严重的。
- **缓存**：复用 `CacheService`，delay-analysis 结果按 user scope 缓存（15min），任务变更时 `clearAll` 失效（现有机制）。
- **N+1 查询规避**：P5 先查 Top N 成员（1 次查询），再批量查趋势（1 次GROUP BY assignee, week），不逐人查。
- **TaskService singleton**：复用 `taskService` 单例（fixed19），不 new。

## 12. 待确认/风险

- **严重度分桶阈值**（轻<7/中7-30/重>30）：暂定，实现后可调。
- **P5 成员趋势 Top N = 10**：暂定，可调。
- **原因×责任人交叉矩阵**（P2）：若原因/人员过多，矩阵稀疏，可能需限制 Top 原因 × Top 责任人。
- **T8 预估偏差**：仅完成延期任务有 `actual_duration`，样本可能偏少，需 UI 提示样本量。
