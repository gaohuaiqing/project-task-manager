# 延期双视角统计 设计文档

> 日期：2026-11-06
> 状态：待用户审阅

## 1. 背景与问题

现状 `delay_count`（累计延期次数）的统计口径是 **`SUM(任务.delay_count) GROUP BY 任务当前 assignee`**：任务换责任人后，历史延期账目全部跟新责任人走，无法回答「这个人负责期间延期了几次」。

数据层基础已存在约 80%：
- `delay_records` 表（迁移 024）：cron 每天 01:00 扫描（`index.ts:324`），每次新延期事件自动写一条
- `workflow/service.ts:735` 延期事件累加 `delay_count` + `:741` 写 `delay_records`

**缺口**：`delay_records` 不记录「延期发生时的负责人」快照。

## 2. 目标（双视角定义）

| 视角 | 回答的问题 | 展示内容 |
|---|---|---|
| **任务视角** | 这个任务累计延期几次？每次是什么时候、当时谁负责？ | 任务详情延期记录 + 「当时负责人」列；报表「延期事件明细表」 |
| **责任人视角** | 时间范围内每人延期几次？分别是什么任务、什么时候？ | P3 成员榜事件归属口径 + 点成员下钻事件列表 |

用户原始例子：一个任务换了 3 个责任人，累计延期 10 次（第 1 人任内 6 次、第 2 人任内 4 次）→ 任务视角显示 10 次及每次归属；责任人视角第 1 人 6 次、第 2 人 4 次。

### 3.2 2026-11-06 方案修正：归零 → 回填

**新证据**（用户提示 + 本机库验证）：`task/service.ts:1020` 每次责任人变更写审计日志，结构化且带时间戳：

```
audit_logs: target_id(任务) + created_at(变更时间) + before_data/after_data(JSON 含 assignee_id)
本机库实测：62 条变更记录 / 229 条延期事件 / 123 个有延期记录的任务
```

**修正决策**：
| 项 | 结论 |
|---|---|
| 历史数据 | **全部保留**，按变更时间轴回填 `assignee_id`，历史延期事件重建归属 |
| 执行方式 | 生产数据下行本机 → **dry-run 出回填映射报告** → 用户确认 → 执行回填 |
| 物理备份 | 回填前 mysqldump `delay_records` + `wbs_tasks(id, assignee_id, delay_count)` 快照回传本机存档（稳妥习惯不变） |

## 4. 数据层设计

### 4.1 迁移 `065-delay-event-assignee.ts`（幂等，无破坏性操作）

| 步骤 | 操作 | 说明 |
|---|---|---|
| ① 加列 | `delay_records` 加 `assignee_id INT NULL` + 索引 | 「当时负责人」快照；NULL = 未知/未分配 |
| ② 回填 | 按变更时间轴 UPDATE 历史 `delay_records.assignee_id` | 详见 4.2；`WHERE assignee_id IS NULL` 天然幂等，可重跑 |

**对比原归零方案**：无归档表、无 TRUNCATE、无 `legacy_delay_count` 字段、`delay_count` 保持原值（与历史事件数天然一致，无需归零）。

### 4.2 回填算法（时间轴推算）

```
对每个任务 T：取其变更记录（audit_logs: details 含「负责人变更」 AND target_id=T）
按 created_at 升序 → 时间轴 [(t1, A→B), (t2, B→C)…]

对每条历史延期事件 e：
  e.created_at ≥ 最后一次变更时间   → 任务当前 assignee（最可靠）
  ti ≤ e.created_at < ti+1        → 第 i 次变更后的值（after_data.assignee_id）
  e.created_at < t1（最早变更记录） → 第一次变更前的值（before_data.assignee_id）
任务从未有变更记录                  → 当前 assignee
after_data.assignee_id 为 JSON null → 记 SQL NULL（当时未分配）
```

同秒多条变更按 `created_at DESC, audit_id DESC` 排序取最新。

### 4.3 已知数据质量边界（本机旧快照实测，生产待 dry-run 确认）

- 早期审计记录 `target_id=NULL`（本机 62 条中 26 条，42%）——无法关联任务，对回填不可用；新记录完整
- **残留误差**：若任务换过 2 次人但早期那条变更记录缺 `target_id`，早期事件会错算给「第一条可见记录的 before 值」。此误差无法从数据内部检测，靠 dry-run 报告抽样人工核对
- 生产库记录比本机新，预期覆盖率更好；真实覆盖率以 dry-run 为准

### 4.4 dry-run 机制（生产执行强约束）

```
本机 dev 验证（生产数据下行）→ tm-test 验证 → 生产上线时：
  ① mysqldump delay_records + wbs_tasks(id, assignee_id, delay_count) 快照回传本机   ← 只读
  ② 生产库跑 dry-run 只读查询：回填映射统计（总事件数 / 回填为当前值 / 时间轴值 /
     无变更记录兜底 的分布、变更记录 target_id=NULL 数、抽样任务明细）
  ③ 报告给用户确认 → 确认后执行迁移（加列+回填）
```

dump 文件存本机项目外目录（如 `G:\Project\Backup\`，带日期命名；生产数据绝不进 git）。

### 4.5 写入点改造（`workflow/service.ts:741`）

`createDelayRecord` 增加 `assignee_id: task.assignee_id` 快照（该上下文 `task.assignee_id` 已可用，`service.ts:750` 在用）。迁移后新事件实时带快照，不再依赖回填。未分配任务记 NULL，展示层显示「未分配」。

### 4.6 口径切换（旧口径 4 处消费点全部切换）

`SUM(delay_count) GROUP BY 当前assignee` → `COUNT(delay_records) GROUP BY assignee_id`（时间范围内）：

| 消费点 | 位置 |
|---|---|
| 统计卡 | `analytics/repository.ts:1103`、`:1118` |
| 图表①责任人 | `analytics/repository.ts:1289` |
| 组对比 | `analytics/repository.ts:1349` |

**不动的**：任务级 `delay_count` 展示（任务详情「累计延期次数」）语义正确、值保持连续。

## 7. 错误处理

- 事件明细空态 → 「时间段内无延期事件」
- `assignee_id` NULL → 显示「未分配」（新事件）或「无快照」（回填无法确定的边界情况）
- 所有新查询参数化（沿用现有 repository 模式）
- mysql2 SUM/COUNT 返回 DECIMAL 字符串 → `Number()` 强转（沿用 `repository.ts:1500` 既有教训）

## 10. 风险与备注

- **回填误差不可完全消除**：`target_id=NULL` 的早期变更记录导致部分任务时间轴不完整，早期事件可能错算（见 4.3）；缓解 = dry-run 抽样核对 + 用户知情确认
- 生产执行仍有数据变更（回填 UPDATE），严格走 4.4 流程（dump → dry-run → 确认 → 执行）
- 迁移后报表 P3 等指标数值会与旧口径不同（这正是本功能目的：从「当前归属」变为「当时归属」），上线说明需告知用户口径变化
- 回填 SQL 涉及 JSON 函数（`JSON_EXTRACT`/`CAST`），MySQL 8.4 已验证可用（生产同为 MySQL 8.x）
