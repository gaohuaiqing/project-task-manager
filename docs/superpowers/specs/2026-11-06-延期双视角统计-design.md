## 1. 背景与问题

现状 `delay_count`（累计延期次数）的统计口径是 **`SUM(任务.delay_count) GROUP BY 任务当前 assignee`**：任务换责任人后，历史延期账目全部跟新责任人走，无法回答「这个人负责期间延期了几次」。

数据层基础已存在约 80%：
- `delay_records` 表（迁移 024）：cron 每天 01:00 扫描（`index.ts:324`），每次新延期事件自动写一条
- `workflow/service.ts:735` 延期事件累加 `delay_count` + `:741` 写 `delay_records`

**缺口**：`delay_records` 不记录「延期发生时的负责人」快照。

## 2. 目标（双视角定义）

| 视角 | 回答的问题 | 展示内容 |
|---|---|---|
| **任务视角** | 这个任务累计延期几次？每次是什么时候、当时谁负责？ | 任务详情延期记录 + 「当时负责人」列；报表「延期事件明细表」 |
| **责任人视角** | 时间范围内每人延期几次？分别是什么任务、什么时候？ | P3 成员榜事件归属口径 + 点成员下钻事件列表 |

用户原始例子：一个任务换了 3 个责任人，累计延期 10 次（第 1 人任内 6 次、第 2 人任内 4 次）→ 任务视角显示 10 次及每次归属；责任人视角第 1 人 6 次、第 2 人 4 次。

### 3.2 2026-11-06 方案修正：归零 → 回填（v2：回填锚点改用延期事件通知直连）

**第一轮修正**（用户提示「系统有责任人变更记录可支持刷新」）：确认 `task/service.ts:1020` 写变更审计 → 拟按审计时间轴回填。

**第二轮修正**（Task 1 实施时证伪审计锚，2026-11-06）：
- `audit_logs.target_id` 是 **INT 列**，AuditService 写入 `parseInt(任务UUID)` → 截断值（36 条）/NULL（26 条），与 UUID 任务无可靠映射（设计阶段「28 任务可关联」的验证系 MySQL INT=VARCHAR 隐式转换假象）
- 截断值启发式反推撞车严重（target_id=4 匹配 8 个任务、6 匹配 11 个），不可用
- task_assigned 通知时间轴方案亦被否决：转派时 `task/service.ts:1035` 删除旧负责人的通知，非 append-only
- **最终锚点（验证通过）**：cron 写 delay_records 的**同一循环**发 `task_delayed` 通知给**当时负责人**（`task_id` 正确 UUID + `user_id`=当时 assignee + 同秒时间戳）→ **事件级 1:1 直连**

本机库（生产 09-28 副本）实测：229 事件中 **226 条 ±120s 唯一匹配**通知（0 歧义）、3 条无匹配（2026-04-29~05-05 通知功能上线前）。

**修正决策**：
| 项 | 结论 |
|---|---|
| 历史数据 | **全部保留**，按 task_delayed 通知直连回填 `assignee_id`，无匹配行以当前 assignee 兜底 |
| 执行方式 | 生产数据下行本机 → **dry-run 出回填映射报告** → 用户确认 → 执行回填 |
| 物理备份 | 回填前 mysqldump `delay_records` + `wbs_tasks(id, assignee_id, delay_count)` 快照回传本机存档（稳妥习惯不变） |

**附带发现（backlog，不纳入本轮）**：AuditService `parseInt` 截断 target_id 是生产 bug——审计日志的任务关联自系统上线即损坏（影响所有任务类审计追溯，不止本功能），须单独评估修复（涉及列类型/写入行为）。

## 4. 数据层设计

### 4.1 迁移 `065-delay-event-assignee.ts`（幂等，无破坏性操作）

| 步骤 | 操作 | 说明 |
|---|---|---|
| ① 加列 | `delay_records` 加 `assignee_id INT NULL` + 索引 | 「当时负责人」快照；NULL = 未知/未分配 |
| ② 回填 | 按变更时间轴 UPDATE 历史 `delay_records.assignee_id` | 详见 4.2；`WHERE assignee_id IS NULL` 天然幂等，可重跑 |

**对比原归零方案**：无归档表、无 TRUNCATE、无 `legacy_delay_count` 字段、`delay_count` 保持原值（与历史事件数天然一致，无需归零）。

### 4.2 回填算法（通知直连，v2）

```
对每条历史延期事件 e：
  存在 task_delayed 通知 n：n.task_id = e.task_id（UUID 精确相等）
    且 |n.created_at − e.created_at| ≤ 120 秒
    → e.assignee_id = n.user_id（cron 同循环写入，即「当时负责人」快照）
  无匹配通知，且事件时间 ≥ 该任务任一条 task_assigned 通知时间
    → 当前 assignee 兜底（通知缺失，但事件时任务已有指派）
  无匹配通知，且事件早于该任务全部 task_assigned 通知（当时未分配）
    → 保持 NULL（展示「未分配」）
```

- 歧义防护：±120s 内多条通知时取时间差最小的一条（ROW_NUMBER 窗口；本机实测 0 例歧义，防护面向生产）
- 幂等：`WHERE assignee_id IS NULL` 天然可重跑
- 回填后 NULL 语义唯一：「延期发生时任务未分配」（不能确定当时具体负责人的极罕见边界归入当前值兜底分支，不产生 NULL）

### 4.3 已知数据质量边界（本机=生产 09-28 副本实测，生产以 dry-run 为准）

- task_delayed 通知自 2026-04-30 起存在；229 事件中 226 条直连匹配（含 04-30~05-05 的早期事件，均有通知）
- 3 条无匹配 = 事件发生时任务未分配（任务 56a47beb：事件 07-11/07-25/09-08，首次指派 09-17）→ 按算法记 NULL「未分配」（当时无负责人，延期事件无通知即因 cron 只通知负责人）
- **本机实测：226 条可匹配事件的「当时负责人」100% 等于当前 assignee**——现存数据中转手与延期无交集，回填后各报表数字与旧口径一致（无突变，回归验证友好）
- 已知轻微低估边界：若任务在事件前有过一次**无通知**的指派（如 2026-08-05 批量操作中有 8 条转手无 task_assigned 通知），该段事件会记「未分配」而非当时的实际负责人——保守方向（不会错记给他人），dry-run 报告呈现
- 生产库新于本机副本一个多月，09-28 之后的转手+延期组合可能存在真实归属差异，以 Task 8 生产数据 dry-run 报告为准
- notifications 无清理机制（delay_warning 自 04-29 全量在库），通知锚点不因清理失效

### 4.4 dry-run 机制（生产执行强约束）

```
本机 dev 验证（生产数据下行）→ tm-test 验证 → 生产上线时：
  ① mysqldump delay_records + wbs_tasks(id, assignee_id, delay_count) 快照回传本机   ← 只读
  ② 生产库跑 dry-run 只读查询：回填映射统计（总事件数 / 通知直连匹配数 / 无匹配兜底数 /
     匹配值≠当前值的事件分布、抽样任务明细）
  ③ 报告给用户确认 → 确认后执行迁移（加列+回填）
```

dump 文件存本机项目外目录（如 `G:\Project\Backup\`，带日期命名；生产数据绝不进 git）。

## 7. 错误处理

- 事件明细空态 → 「时间段内无延期事件」

- mysql2 SUM/COUNT 返回 DECIMAL 字符串 → `Number()` 强转（沿用 `repository.ts:1500` 既有教训）

## 10. 风险与备注

- **回填误差边界**（见 4.3）：仅通知功能上线前（2026-05-05）的早期事件走当前值兜底；生产库新增数据可能出现「匹配值≠当前值」的真实归属差异，dry-run 报告逐条呈现供确认

- 生产执行仍有数据变更（回填 UPDATE），严格走 4.4 流程（dump → dry-run → 确认 → 执行）
- 迁移后报表 P3 等指标数值会与旧口径不同（这正是本功能目的：从「当前归属」变为「当时归属」），上线说明需告知用户口径变化
- 回填 SQL 使用窗口函数（ROW_NUMBER）与 TIMESTAMPDIFF，MySQL 8.x 支持（生产同为 MySQL 8.x，已在本机 8.4 验证）

### 11.2 需求 B：计划变更历史同款双视角处理

**口径决策（用户 2026-11-09 确认）**：
- 「变更事件」= **仅已生效变更**（approved：直接变更 + 审批通过；不含 rejected/timeout/pending）
- **批次级计数**：一次提交多字段 = 1 个事件（`COUNT(DISTINCT COALESCE(pc.submission_id, pc.id))`，submission_id NULL 的旧行按 id 自成一批），与旧 plan_change_count「一次提交 +1」的量纲一致
- 计划变更排行（P3 第 3 专项）**加事件下钻弹窗**（与延期次数排行同款交互）

#### 11.2.1 数据层：迁移 `066-plan-change-event-assignee.ts`（幂等，无破坏性操作）

- `plan_changes ADD COLUMN assignee_id INT NULL`（变更生效时任务负责人快照，NULL=当时未分配）+ 索引 `idx_pc_assignee (assignee_id)`；不加外键（同 065 理由）
- **回填：指派通知区间法**（plan_changes 无 task_delayed 式同秒通知锚，改用 task_assigned 通知序列重建指派时间轴）：
  - 生效时点 `eff_time = COALESCE(pc.approved_at, pc.created_at)`（approved 行用审批通过时间，pending/timeout 用创建时间）
  - 归属 = 该任务**最后一条 `eff_time ≥ n.created_at` 的 task_assigned 通知**的 `user_id`；无匹配（生效早于全部指派通知）→ 保持 NULL = 当时未分配
  - 无额外「当前值兜底」：区间法自洽（有匹配即归属，无匹配即未分配；与 065 兜底② EXISTS 语义等价）
  - 已知误差边界：转派时 `deleteNotificationsByTaskAndUser` 会删旧负责人的通知（时间轴断链，时点可能错记给相邻区间负责人）——dry-run 统计匹配率 + 抽样核对，误差接受并报告
- 幂等三重保护同 065（migrations 表 + INFORMATION_SCHEMA + `WHERE assignee_id IS NULL`）
- 生产现状（2026-11-07 副本）：plan_changes 318 条（approved 291=直接 230+审批 61 / timeout 24 / pending 3），字段分布 duration 266 / start_date 51 / predecessor_id 1
